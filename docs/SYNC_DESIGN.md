# 同期とアカウントの設計

前提: **相手がアプリを入れなくても、1人で全部使えること。**
それが崩れる設計は、調査でいちばん重い壁（パートナーがインストールしない）に負ける。

---

## 0. 結論

1. **保存は端末の中**（ローカル優先）。サーバーは「あとで突き合わせる場所」でしかない
2. **家族の識別にメールもログインも使わない**。世帯idと世帯トークン、端末idだけで足りる
3. **同期は追記のみのop（操作ログ）**。上書きしない・消さない。突き合わせれば、どの端末でも同じ状態になる
4. **同期はREST 4本**（opの出し入れ pull / push ＋ 世帯の始末 削除 / トークン作り直し）。リアルタイム購読は入れない。開いたとき・追加したときに送るだけ
5. **相手が入れない前提を3段階で支える**（下の図）。どの段階でも、こちらの全機能は使える
6. **同期は無料にしない**（2台以上・世帯共有から課金）。1人利用は無料で全機能。広告は入れない

---

## 1. 制約（これが方式を決める）

| 制約 | 設計への効き方 |
|---|---|
| 相手が入れないかもしれない | 単独動作が既定。共有は「あとから足せる機能」 |
| メール登録・ログインをさせない | 本人確認をしない。端末が本人。世帯トークンが鍵 |
| オフラインで書ける | 端末に書いて後で送る。サーバーが落ちていても書ける |
| 2人世帯・小さなテキスト | 同時編集は稀。凝った競合解決は要らない |
| 個人開発・無料枠 | サーバーは2エンドポイント。常時接続の購読は持たない |

## 2. インストール不要をどう支えるか

```
L0: 1人だけ（既定）
    端末の中だけで完結。サーバーもアカウントも不要。
    ── 調査でいう「LINEより軽い」はここで満たす

L1: 相手はブラウザだけ（インストール不要）
    同じFlutterコードをWebビルドして、アプリと同じドメインに置いておく。
    「招待リンク」を送る → 相手はブラウザで開く → そのまま参加
    「1件リンク」を送る → 相手は本文を見て「やる／あとで」だけ押せる（アカウント不要）

L2: 相手がアプリを入れた
    同じ世帯コードで参加。ここで初めて「入れなくても使える」を卒業する
```

**1件リンク**が実は一番効く。調査でいう「LINEで送るより面倒なら負ける」への答えで、
LINEで送ったURLを開けば、アプリを入れていない相手でも中身が見えて、担当を引き受けられる。
アプリの存在を知ってもらう導線も兼ねる。

### 1件リンク（実装済み・テスト済み）

[lib/one_link.dart](../lib/one_link.dart) がURL、[lib/one_page.dart](../lib/one_page.dart) が相手に見せるページ。

```
https://<アプリとAPIのドメイン>/#one?i=<案件id>&h=<世帯id>&t=<世帯トークン>&m=<メンバー>
```

| | 決めごと |
|---|---|
| 断片に置く | 世帯トークンは `#` の後ろ（**断片はサーバーに送られない**ので、アクセスログに残らない）。クエリに置くと、プロキシやログに鍵が残る |
| 何を渡すか | `i` 案件id／`h` 世帯id／`t` トークン／`m` 引き受ける人（相手は自分の名前を持たないので、送る側が決める）。開発中はポートが違うので `api=<APIの場所>` を足せる |
| 読めないときは読まない | トークンが短い・世帯や案件が欠けている・http(s)でない のいずれかなら、**ページを出さず**、ふつうのアプリとして起動する |
| 取りに行く範囲 | `GET /ops?...&issue=<案件id>`。**その1件のopだけ**を返す（相手のブラウザに世帯の記録を置かない） |
| 失効 | `&e=<期限の時刻>` を付けると、過ぎたリンクは読まない（無ければ無期限。送るときは7日を付ける）。期限切れを開いても、ただのアプリになる |
| 相手にできること | 中身を見る・「やる」・「あとで」。それ以外の操作は出さない |
| 端末に残さない | 相手のブラウザにストレージを渡さない（端末idも保存しないので、開くたびに新しくなる）。cursorもメモリの中だけ |
| 担当の言い方 | 開いた人から見た言い方にする。このリンクで引き受ける人を「自分」、それ以外を「ほかの人」（世帯の呼び名は、持っている側の都合で開いた人には分からない） |
| 「やる」の中身 | `assignee` opを1つ書いて、その場で送る。**送れなかったときは書いたまま残し、押し直しでは書かずに送り直す**（同じ担当のopを増やさない） |
| 誰として | `m` のメンバーid。世帯の `members` に対応する行が無くても、担当はidで残る（表示名は後から付けられる） |

## 3. サーバーに置くもの

| テーブル | 中身 |
|---|---|
| `households` | 世帯id、作成日時 |
| `ops` | 世帯id、op_id、device_id、lamport、kind、issue_id、payload(JSON)、端末時刻 |
| `members` | 世帯id、member_id、表示名（「自分」「パートナー」を後から変えられるように） |

opの出し入れは2本だけ。**opは追記のみなので、上書き事故が起きない。**
世帯の始末（削除・トークン作り直し）を足して計4本。

```
GET  /ops?household=<id>&since=<cursor>   増分をもらう
POST /ops                                 自分のopを送る（op_id が主キーなので、二重送信しても安全）
DELETE /ops?household=<id>                世帯を消す（opと世帯の行。端末の記録は残る）
POST /household/rotate                    トークンを作り直す（古い招待文は失効。opとcursorはそのまま）
```

- `cursor` はサーバー採番の単調増加（挿入順）。世帯ごとに独立
- 1件が数百バイトのテキストなので、数年分でも全件取得で足りる。凝った差分管理は不要
- **リアルタイム購読は入れない**（WebSocket/購読を常時持つと運用が重くなる）。取りに行くのは
  起動時・アプリ復帰時・自分が書いた直後の3回

### 実装した契約（[server/](../server/README.md)）

```
GET  /ops?household=<id>&since=<cursor>[&limit=<n>][&issue=<案件id>]
POST /ops   {"household": "<id>", "ops": [ ... ]}
```

| | 決めごと |
|---|---|
| 認証 | `Authorization: Bearer <世帯トークン>`。トークンは **SHA-256のハッシュだけ**を保存（平文は持たない） |
| 絞り込み | `issue` を付けると、その1件のopだけを返す（1件リンクのページ用）。cursorの意味は変わらない |
| 絞り込みの中身 | その1件のopが最後に来る位置を `cursor` にする。誰も知らない案件idを指しても、空で返るだけ（世帯の存在を漏らさない） |
| 世帯 | 最初のアクセスで作られる。**そのとき提示されたトークンが、その世帯の鍵になる** |
| 応答 | `{"cursor": n, "ops": [...], "skipped": 0}`。`cursor` は「ここまで返した」位置で、端末はこれをそのまま覚える |
| ページング | `limit`（既定1000、`0`で無制限）。端末は空が返るまで `since=cursor` で繰り返す（サーバー側の上限も、応答の取りこぼしも、同じ回路で吸収できる） |
| 送信 | 1回200件まで。1件でも形が壊れていれば**まとめて400**（中途半端に預けると、端末の送信待ちが消えてしまう） |
| 削除 | `DELETE /ops?household=<id>`。opと世帯の行を消す。消した後の最初のアクセスで空の世帯が作り直される |
| 作り直し | `POST /household/rotate {"household": "<id>", "token": "<新しいトークン>"}`。古いトークンで認証し、新しいハッシュに置き換える。短いトークンは400 |
| 二重送信 | `op_id` が主キー。すでにあれば増えず、cursorも進まない |
| 壊れた行 | 読めないpayloadは飛ばして返す（1件のせいで世帯が読めなくならない） |
| 失敗 | `401`（トークン違い）／`400`（形が違う）／`500` |

端末側の結線は [lib/sync/api.dart](../lib/sync/api.dart)（HTTP）と [lib/sync/session.dart](../lib/sync/session.dart)（送って・もらって・
足りない「次の1件」を書いて・また送る）。opのJSONは [lib/sync/wire.dart](../lib/sync/wire.dart) が両端の約束になる。

### 世帯の作り方

`households` に行を作るAPIは無い。**最初のアクセス（GETでもPOSTでも）が、世帯の作成になる。**
そのとき送られてきたトークンのハッシュを保存し、以後はそれと一致しないと読めない・書けない。
だから世帯idもトークンも、推測できない乱数にすること（招待リンクに埋め込む2つ）。
トークンを失ったら、新しい世帯を作り直して招待し直す（再発行は未実装。§10）。

## 4. 突き合わせの規則（実装済み・テスト済み）

参照実装: [lib/sync/log.dart](../lib/sync/log.dart) / テスト: [test/sync_log_test.dart](../test/sync_log_test.dart)

| 規則 | 内容 | なぜ |
|---|---|---|
| 並び順 | lamport → 端末id → op_id | 端末の時計がずれても、どの端末でも同じ並びになる |
| 各項目 | 最後のopが勝つ | リアルタイムな同時編集が稀なので、これで足りる |
| 完了 | 有効な完了は**最初の1つだけ** | 2台が別々に完了しても、状態が二重にならない |
| 次の1件 | id を `next:<完了opId>` と決定的に導く | どちらの端末が作っても同じ案件idになるので1件に畳まれる |
| 取り消し | `reopen` op。状態を戻す操作（やることにもどす）も同じ扱いにする | 端末の時計に頼らず、元に戻せる |
| 元を失った「次の1件」 | 射影の段階で見えなくする。**消すopは書かない**。連鎖して生まれた1件にも伝播する | 突き合わせ直後に同じ名前の行が2つ見えるのを防ぐ。消すopを書くと復活できない |
| 元の案件が消されたとき | 次の1件は**消えない**。隠すかどうかは「元の完了が取り消されたか」だけで決める。完了が有効なら、次の1件も無ければ作る | 過去の記録を整理しても、定期の連なりは続く。止めたいときは「くりかえし: なし」にする |
| 同じ系列で追い越された1件 | 見えている中でいちばん新しい1件だけを「いまの1件」とし、古い1件は射影で隠す（`superseded`） | 増分同期でopが欠けると系列のつながりが切れ、元の案件と次の1件が同時に見える。全件そろっていれば何も起きない |
| 消されたもの | 作り直さない（利用者が消したものを勝手に戻さない） | 「これは要らない」を消せるようにする |

検証している振る舞い（同期関連13件）:

- 2台がオフラインで別々に完了 → 突き合わせると、次の1件は**1つだけ**（朝に完了した方の日付が採用される）
- 取り消すと、そこから生まれた次の1件も消える（両端末で同じ結果）
- 定期でない案件を完了しても、次の1件は作らない
- 別々に追加したものは両方残る（idが衝突しない）
- 同時についたコメントは両方残り、並び順も一致する
- 端末の時計が1時間ずれていても、順序は論理時計で決まる
- 同じop集合なら、並べる順が違っても同じ結果（収束する）
- 完了済みを「対応待ち」に戻すと、自動生成された次の1件は見えなくなる
- 消した「次の1件」は、あとから作り直されない
- 元を失った1件から更に生まれた1件も、まとめて見えなくなる（連鎖）
- 完了済みの元を消しても、次の1件とその先の連なりは残る（過去の記録を整理しても連なりは切れない）
- 元が消されたあとに完了が届いても、次の1件は作られる（片方で完了・もう片方で削除を同時にしても連なりは続く）
- 相手のopを受け取ると、次に自分が書くopの番号は相手より後になる

### ランダム操作で壊しにいった結果（設計ミス3件を発見して修正）

[test/sync_fuzz_test.dart](../test/sync_fuzz_test.dart) で、3台の端末にランダムな操作（追加・改名・担当変更・期限変更・繰り返し変更・コメント・状態変更・完了・取り消し・削除）を
**80通り × 350手 = 2.8万手**当てて、部分的な同期を挟みながら、最後に全員が同じ状態になるかを確かめている。
探すのは「収束」「同じ定期案件が同時に2つ見えない」「元を失った派生が見えない」「完了したら次の1件がある」「タイトルの無い案件が見えない」の5つ。

この検証で、机上では気づかなかった設計ミスが3件見つかった。3件とも修正済み。

| 見つかった問題 | 何が起きるか | 直し方 |
|---|---|---|
| 元を失った派生を `delete` で消していた | 後から古い完了opが届いて再び必要になっても、消えているので復活できない（永久に行方不明） | 消さずに**射影で隠す**。opは追記のみという方針とも一致する |
| 派生の連鎖を一段しか見ていなかった | 元を失った1件から更に生まれた1件が見えたまま残り、同じ定期案件が2つ同時に見える | 作られた順に判定して、**連鎖に伝播**させる |
| 完了済みに「対応待ち」を書き戻すと、完了の記録が残ったまま未完了に戻る | 元に戻した案件と、自動生成された次の1件が同時に見える | 状態を完了以外に戻すopは、**完了も取り消したものとして扱う** |

いまの画面では「3つ目」の操作は作れない（完了した案件は一覧から消えるため）が、opは追記のみなので、
後から順不同で届いたり、画面に別の導線が増えたりすると必ず起きる。記録の側で矛盾が起きないようにしてある。

### 増分同期で取りこぼしても壊れないか（4件目を発見して修正）

[test/sync_incremental_test.dart](../test/sync_incremental_test.dart) では、サーバー役に挿入順の cursor を振り、
`GET /ops?since=` の**取りこぼし（応答の途中が抜ける・cursorの飛び越し）／重複配信／順不同配信／cursorの巻き戻し**を
混ぜて、3台に **200通り × 250手** 当てている。確かめるのは次の2つ。

1. **欠けても壊れない** — 途中の射影が自己整合であること（同じ系列の未完了が2つ見えない／元を失った派生が見えない）
2. **いつか必ず直る** — 全件（`since=0`）を取り直し、足りない「次の1件」を書き切れば、どの端末も同じ状態に収束すること

この検証で4件目の設計ミスが見つかった。

| 見つかった問題 | 何が起きるか | 直し方 |
|---|---|---|
| 途中の1件がまるごと欠けると、系列のつながりが切れる | 端末にデータが無いだけなのに、元の案件と先の1件が**同時に未完了で見える**（同じ定期案件が2つ） | 見えている中で**いちばん新しい1件だけ**を「いまの1件」とし、追い越された1件は射影で隠す（`superseded`）。全件そろえば何も起きない |

3件目までは「突き合わせ直後に2つ見える」問題だったが、これは**欠けたまま**でも見えないようにするための規則。
`addOrder` は親の完了opより必ず後になる（因果順）ので、「見えている中で最大の `addOrder`」が系列の先頭になる。
全件が届けば古い1件はすでに完了しているため、この規則は何もしない（収束後の射影に `superseded` は1件も残らないことをテストで確かめている）。

## 5. サーバーの選定（カタログを調べた結果）

同期先を探したが、**「オフライン優先＋匿名ID」を一発で満たす専用サービスは手元のサービスカタログには無かった**
（PowerSync / ElectricSQL / Replicache のような専用同期エンジンは未収載）。
そこで、汎用の部品を組み合わせる前提で比較した。

| 候補 | 評価 | この企画での見え方 |
|---|---|---|
| **Cloudflare Workers + D1**（推奨） | 86 | SQLite。**Web版アプリ・招待リンク・APIを同一ドメインで配信できる**。無料枠。APIは2本だけ |
| Turso | 88 | エッジSQLite。同じ2本のAPIをlibSQLで。Web配信は別途必要 |
| Neon | 92 | サーバーレスPostgres。実績は十分だが、Web配信は別途 |
| Convex | 82 | リアクティブBaaS。購読が要らない設計なので旨味が薄い |
| Firestore / Realtime Database | 50 | **サーバーコード0本**（匿名認証＋オフラインキャッシュ内蔵）。ただしSDKが重く、依存が増える |

**推奨: Cloudflare Workers + D1。**
理由は「相手がインストールしない」制約と噛み合うから。**アプリ本体（Web版）・招待リンク・同期APIが1つのドメインで完結**するので、
相手に渡すURLが1本で済み、証明書もCORSも考えなくていい。同期APIが2本だけなので、Workerは100行未満で書ける。

**実装済み**（[server/](../server/)）。D1 を作って、スキーマを流して、デプロイするだけ。

```bash
cd server
npx wrangler d1 create ie_koto                              # 出た database_id を wrangler.toml に貼る
npx wrangler d1 execute ie_koto --remote --file=./schema.sql
npx wrangler deploy
```

Cloudflare のアカウントが無くても、**手元で同じ Worker を動かして試せる**（D1 だけ `node:sqlite` で真似る）。

```bash
cd server
npm test                                  # 14件（本物のSQLで確かめている）
npm run serve -- --port 8799              # アプリの接続先にできる
```

アプリ側は、ビルドのときに世帯idとトークンを渡す（画面がまだ無いため。[lib/sync/config.dart](../lib/sync/config.dart)）。

```bash
flutter run -d web-server --web-port 8080 \
  --dart-define=IE_KOTO_API=http://127.0.0.1:8799 \
  --dart-define=IE_KOTO_HOUSEHOLD=hh_... \
  --dart-define=IE_KOTO_TOKEN=...
```

Trade-off: **サーバーコードを1行も書きたくなければ Firestore**（匿名認証とオフラインキャッシュが組み込みで、
「メール不要」という要件に一番素直に合う）。ただしFlutter側の依存が重くなり、
この企画の「軽い」という性格と、いまの依存ゼロに近い構成（`flutter` と `flutter_localizations` だけ）からは離れる。

## 6. アカウント（メールを使わない）

- **世帯トークン**: 32バイトのランダム。世帯に1つ。招待リンクに埋め込む。
  サーバーは平文を持たず、SHA-256 のハッシュだけで照合する（[server/src/ops.js](../server/src/ops.js)）
- **端末id**: 初回起動で生成して端末に保存。同期の名義人
- **member_id**: `me` / `partner` のような固定idに表示名を対応させる。opに書いた人（`member`）が残り、履歴の「だれが」に出る。この端末を使う人と表示名は、ホームの世帯名→シートで変える（端末ローカルに保存し、同期しない）
- **入れ替え**: 端末を失ったら招待リンクを再発行 → 古いトークンでは書けなくする
- **漏れたときの影響**: その世帯の家のことだけ。他人の世帯は読めない
- **削除**: 世帯単位で完全削除。書き出し（エクスポート）も用意する

家の中身がサーバーを通る点は、隠さずに書く（端末をまたぐ共有には避けられない）。
画像を同期しないのも、この露出を小さく保つため。

## 7. 課金の置き場所

| 範囲 | 価格 |
|---|---|
| 1人で使う（保存・定期・履歴・通知） | 無料。全機能 |
| 相手を招待して同期する（2台以上・世帯共有） | 有料（Todyの型: 年$25相当） |

調査で、無料の家事アプリの不満は「広告で操作が中断される」「無料版は2ヶ月以上前の記録が見られない」だった。
**軽さを売る企画が広告を入れると矛盾する。** 無料版は機能を削らず、広告も入れない。
課金の線を「1人か、家族か」に引くのが、この企画では一番説明しやすい。

## 8. アプリ本体をop logに載せ替えた（手順2・完了）

[lib/store.dart](../lib/store.dart) の `IssueStore` は、opを追記して射影し直す形になった。
画面が見る形（`Issue`）は、毎回の射影から組み直す。**UIと既存のテストは変えていない。**

| 前 | いま | 効いていること |
|---|---|---|
| `IssueStore.nextId()` の連番（`i1`, `i2`） | 案件idは、それを生んだadd opのid（端末id ＋ 論理時計） | 2台で番号が衝突しない |
| 変更メソッドが状態を直接書き換える | opを追記して射影し直す（`_commit` を必ず通る） | 突き合わせる単位ができた。手順3でそのまま送れる |
| 完了時にその場で次の1件を生成し `generatedNextId` に持つ | 決定的id `next:<完了opId>` から射影で導く | 2台が別々に完了しても1件に畳まれる |
| 取り消しで生成した1件を `remove` していた | `reopen` opを書く。生成した1件は**射影で隠れる**だけ | あとから順不同でopが届いても復活できる |
| `seriesId` を完了時に初めて設定 | 追加のadd opで必ず設定し、次の1件へ引き継ぐ | opを合成しても、どの案件の並びか分かる |
| `meId = 'me'` 固定 | 端末idは入った（`IssueStore.deviceId`）。member_idとの対応は手順3 | 履歴の「だれが」は、いまは全部「自分」 |
| メモリのみ | 端末に残す（[lib/sync/storage.dart](../lib/sync/storage.dart)）。opの列と端末idと送信済み位置だけ | 閉じても消えない（手順1・完了） |

`clock` の差し替え（テスト用）はそのまま活かしている。検証は [docs/VERIFICATION.md](VERIFICATION.md)。

射影は書き込みのたびに全件作り直す。家の案件は数年で数千opの想定なので、この素直さを選んでいる。

### 端末に残すもの（手順1・完了）

残すのは4つだけ。**射影（画面に出す形）は残さず、起動時に op から作り直す**
（規則が1つで済むし、射影の形を変えても保存を壊さない）。

| 何を | どこに | なぜ |
|---|---|---|
| opの列 | `ie_koto.ops.<n>`（**200件ずつのまとまり**、1行1つのJSON） | 家の記録そのもの。壊れた行はその1行だけ捨てる |
| 端末id | `ie_koto.device_id` | 案件idとopのidが、端末をまたいでも衝突しないように |
| 送信済みの位置 | `ie_koto.pushed_through` | 起動時に送信待ちを作り直す（自分のopのうち、確認できていないものだけ） |
| 同期の設定 | `ie_koto.sync` | 世帯id・トークン・**cursor**。次からは `--dart-define` を渡さなくていい |

置き場は shared_preferences（Android は SharedPreferences、Web は localStorage）。
**まとまりごとに足す**ので、opが増えても1回の書き込みの重さは変わらない。
全件を書き直す形だと5000opで1タップごとに115msかかった（まとまりにしたら13ms。実測は [VERIFICATION.md](VERIFICATION.md)）。

気をつけていること:

- **送り直さない**: cursor と送信済み位置を残すので、開き直しても全件を送り返さない（二重送信はサーバー側でも畳まれる）
- **opは消さない・書き直さない**: 追記のみ。書き戻しの事故が起きない
- **暗号化はしない**: 端末の中は平文（鍵の置き場を別に作ると重くなる）。家の中身が端末に平文で入る点は、隠さずに書く
- **デモは初回だけ**: 2回目以降は、残しておいたものを開く（触って確かめる用のデータを入れ直さない）

## 8.5 同期をつないだ（手順3・APIと結線まで・完了）

サーバー（[server/](../server/README.md)）と、端末側の結線（[lib/sync/](../lib/sync/)）が入った。

| やったこと | 場所 |
|---|---|
| opの出し入れ（`GET /ops`・`POST /ops`）と世帯の始末（`DELETE /ops`・`POST /household/rotate`）。D1 に `households` / `ops` / `members` | [server/src/index.js](../server/src/index.js) / [server/schema.sql](../server/schema.sql) |
| 送受信のHTTPとエラーの種類分け（offline / unauthorized / bad_request / server / bad_response） | [lib/sync/api.dart](../lib/sync/api.dart) |
| opのJSON（両端の約束。日付は壁時計のまま、くりかえしは入れ子） | [lib/sync/wire.dart](../lib/sync/wire.dart) |
| 送って・もらって・足りない「次の1件」を書いて・また送る。書いた直後の自動送信（まとめ送り） | [lib/sync/session.dart](../lib/sync/session.dart) |
| 送信待ち（outbox）と `settle()` をストアに公開。受信後に足りない「次の1件」を書けるようにした | [lib/store.dart](../lib/store.dart) |

サーバーはopの中身を解釈しない（預かって順に返すだけ）。**突き合わせの規則は端末側のまま**なので、
射影の規則（§4）を変えてもサーバーは触らなくていい。

確かめたこと（[docs/VERIFICATION.md](VERIFICATION.md)）:

- Worker の14件は **schema.sql と src/ をそのまま**動かす（差し替えるのは D1 だけ）。node:sqlite なので本物のSQLが通る
- Dart の30件は、**実際のHTTP**（本物のソケット）で確かめる。ページング・二重POST・応答の途中で切れる・壊れたop
- そのうえで **本物の Worker を Node で起動して**、2台の端末役を実際に収束させる（e2e 3件）
- 実アプリ（Flutter Web）から、デモのopがサーバーに届き、別の端末の完了を拾って「次の1件」を書き戻すところまで確認

**端末の保存**（世帯id・トークン・cursor）も入った（§8の下）。いまは `--dart-define` で渡し、
一度渡せば端末に残る（画面から世帯を作る・参加する導線はまだ無い）。

## 8.6 1件リンク（手順3の「送る」・完了）

相手がアプリを入れていなくても、**ブラウザで1件だけ見て「やる」を押せる**ところまで入った。

| やったこと | 場所 |
|---|---|
| URL（何を含めるか、断片に置く規則、読めないときの扱い） | [lib/one_link.dart](../lib/one_link.dart) |
| 相手に見せるページ（見る・やる・あとで の3つだけ。端末に何も残さない） | [lib/one_page.dart](../lib/one_page.dart) |
| 開いたときの振り分け（リンクなら端末の保存を読まず、そのページだけ出す） | [lib/main.dart](../lib/main.dart) |
| 送る導線（詳細の「そのほか」→「リンクを送る」。同期の設定があるときだけ出す） | [lib/detail_page.dart](../lib/detail_page.dart) |
| サーバーの絞り込み `&issue=<案件id>` | [server/src/ops.js](../server/src/ops.js) |
| 相手の `assignee` op（idは端末ごとの乱数。押し直しでは増やさない） | [lib/one_page.dart](../lib/one_page.dart) の `_take` |

相手のブラウザが投げるのは、`GET /ops?...&issue=<案件id>` と、押したときの `POST /ops` の2本だけ。
世帯のほかの案件は**リクエストの中にも応答の中にも入らない**。

確かめたこと（[docs/VERIFICATION.md](VERIFICATION.md)）:

- URLの往復と断片の扱い（5件）／相手の画面の8件（やる・あとで・終わっている・もう無い・つながらない・送れない・開くたびに別人）／送る側の2件
- 本物の Worker と実HTTPでの通し（2件）。生の応答に、ほかの案件の文字が1つも入らないことも見ている
- 実アプリをブラウザで動かし、リンクを開く→「やる」→ 持ち主の画面に「パートナー」と出るところまで目視

## 9. 実装順（各段階が単独で動く）

1. **保存** — opと端末idを端末に保存。`deviceId` も端末に保存。ここで「1人で使える」が完成した ← **完了**（[lib/sync/storage.dart](../lib/sync/storage.dart)）
2. **op化** — 変更を op に置き換え、[lib/sync/log.dart](../lib/sync/log.dart) の射影に載せる。定期の自動生成と取り消しが決定的になる ← **完了**（[lib/store.dart](../lib/store.dart)）
3. **同期** — Worker に API 4本（← **完了**）と、「送る」（1件リンク ← **完了**。§8.6）。世帯コードを画面から作る・参加する導線も**完了**（ホームの世帯名から開くシート。`--dart-define` があればそちらが最優先で、一度渡せば端末に残る）
4. **Web共有** — Flutter Web ビルドを同一ドメインに配置し、招待リンクで参加できるようにする
5. **通知** — 「自分の担当になった」「期限当日」「朝の要約」の3つだけ。アプリ内のお知らせ1行＋担当通知まで**完了**（OSの通知は未実装）

**1と2と3（API・結線・1件リンク・世帯の画面まで）は終わった。** 閉じても消えず、2台で同じ家を見られ、
アプリを入れていない相手にも1件だけ見せられる。世帯の作成・参加・再発行・削除も画面からできる。
次は手順4（Webビルドを同じドメインに置く）。OS通知（5の残り）は、実際に使い続けられてからで遅くない。
