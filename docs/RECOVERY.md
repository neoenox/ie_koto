# 端末移行とサーバー復旧の手順（#65）

データが失われたときの戻し方。**利用者**（アプリを使う人）と**運用者**（サーバーの管理者）で手順が違う。

## 1. 何がどこに残るか（復旧範囲）

| データ | 端末の書き出し（JSON） | 同期（サーバー） | 再インストール後 |
|---|---|---|---|
| 用事・コメント・担当・状態・期限・定期の連なり | ○（op として入る） | ○（op） | 同期していれば戻る／していなければ書き出しを読み込む |
| 名簿（表示名） | **×**（op ではない） | ○（`members` 表） | 同期していれば戻る |
| 「この端末を使う人」 | **×** | **×**（端末ごとの設定） | もう一度選ぶ（[CONTEXT.md](../CONTEXT.md)） |
| 世帯ID・世帯トークン | **×** | サーバーはハッシュのみ | 招待リンクから再設定、または再発行 |
| 送信済み位置（cursor / pushedThrough） | **×** | **×**（端末に保存） | 消えると全部「未送信」に見えるが、サーバーは op_id で重複を落とす（下記） |

書き出し（`lib/store.dart` の `exportJson`）が持つのは **op だけ**。名簿・本人・世帯の接続は同期の側で戻す。

## 2. 利用者の手順

### 端末を買い替える・入れ直す（同期を使っている場合）
1. 新端末にアプリを入れ、世帯の設定で**招待リンクを読み込む**（世帯ID・トークンを設定）。
2. 起動して同期すると、サーバーから op・名簿・名簿の対応表が戻り、画面が元どおりになる。
3. **「この端末を使う人」を選び直す**（端末ごとの設定なので引き継がれない）。
4. 送信済み位置は端末に無いので、最初は全件を「未送信」として持ちうる。送っても op_id が主キーなので**増えない**（重複しない）。一度取り切れば以降は差分だけ。

### 同期を使わない（または同期先を変える）引っ越し
1. 古い端末: 世帯のシート → **書き出す**（JSONをコピー）。
2. 新しい端末: 世帯のシート → **読み込む**（貼り付け）。
3. 読み込んだ op は**送信待ちに載る**ので、同期を設定すれば共有相手にも届く（#12 で検証済み）。

### 端末を失った
- その端末の中身は本体とともに失われる。同期していれば、別の端末とサーバーに同じ op が残る。
- 心配なときは世帯トークンを**再発行**（rotate）してから、新しいトークンで各端末を再設定する。

## 3. 運用者（サーバー）の手順

### バックアップの取り方
- **Cloudflare D1 の Time Travel**（ポイントインタイム復元）: D1 は既定で過去**30日**まで特定時点へ戻せる（保持期間はプランで変わる）。追加設定なしで使える安全網。
- **手動ダンプ**（Time Travel の窓より前へ戻したいとき・控えを手元に置くとき）:
  ```
  npx wrangler d1 export ie_koto --remote --output=backup-YYYYMMDD.sql
  ```
  これは**全テーブルの全行**（`households` / `ops` / `members` / `member_aliases` / `share_tokens`）を含む。

### 保持方針
- Time Travel: 既定の窓（約30日）をそのまま使う。
- 手動ダンプ: **月に1回**、直近 **3〜6か月**ぶんを保持。**別の場所**（離れたディスク／別クラウド）に、暗号化して置く。
- ダンプには `token_hash`・`op` 本文・表示名が入る。**秘密と同じ扱い**（共有しない・リポジトリに置かない）。

### アクセス管理
- Cloudflare アカウントは**所有者のみ**。2要素認証を必須にする。
- 復元（本番DBへの書き戻し）は所有者が行う。AI・自動化には渡さない。

### 復元する（隔離環境で先に確かめる）
1. **別のDB**を作り、ダンプを入れて壊れていないか確かめる（本番に直接戻さない）。
   ```
   npx wrangler d1 create ie_koto_restore_check        # 検証用（普段は消しておく）
   npx wrangler d1 import ie_koto_restore_check --remote --file=backup-YYYYMMDD.sql
   ```
2. 検証用DBへ `GET /ops?household=<id>&since=0` を投げ、件数と先頭・末尾の op を確認する。
3. 問題なければ本番へ戻す（**新DBへ入れてバインディングを差し替える**のが安全。既存DBへの上書きは避ける）。

### 復旧後の確認（cursor・重複・整合性）
- cursor は世帯の `seq` に紐づく。ダンプは `households.seq` も含むので、**端末が持つ cursor はそのまま使える**。
- 迷ったら端末ごとに `cursor=0` で取り直してよい。`op_id` が主キーなので**重複は作られない**（増えるのは D1 の rows read だけ）。
- 消したはずのものが残っていないか: **削除後に取ったバックアップには残らない**。削除**前**のバックアップには、保持方針の窓のあいだ残る（利用者には「世帯の削除ではバックアップからは即座に消えない」と説明済み。[PRIVACY.md](PRIVACY.md)）。

### サーバーを直前のバージョンへ戻す
- Worker: `npx wrangler rollback`（直前のデプロイへ）。
- スキーマは**追記のみ**なので戻さない（古いコードが新しい列を無視できるようにしてある）。

## 4. 許容する損失と目標

| 目標 | 値 | 根拠 |
|---|---|---|
| RPO（失ってよい直近の幅） | 同期していれば**ほぼ0**（各端末に直前までの op が残る）／サーバーのみなら Time Travel の粒度（分〜時間）／手動ダンプ運用なら最大**1か月** | op は追記のみで、端末とサーバーの両方にある |
| RTO（復旧にかけてよい時間） | Worker ロールバックは**分**、D1 の復元＋差し替えは**数十分** | 別DBへ入れてバインディング差し替え |
| 許容する損失 | 同期も書き出しもしていない端末の記録 | 利用者側の運用（説明済み） |
| 利用者の作業 | 復旧後は**何もしなくてよい**（未送信を保持し、自動で再送） | 端末は送信待ちを保持する |

## 5. この手順の検証（隔離環境・実証済み）

`server/test/backup_restore.test.mjs`（実行: `cd server && npm test`）が、`schema.sql` を当てた**別の in-memory SQLite** へ全行ダンプ→復元して確かめている。本番の `wrangler d1 export` も同じ「全行ダンプ」なので、この検証がそのまま上記手順の根拠になる。

- op の中身と挿入順（`seq`）が戻る
- 世帯の `seq`（cursor の上限）が戻り、**既に cursor=2 まで見ていた端末は続きだけを引ける**
- 二重送信しても増えない（`accepted: 0, duplicates: 1`）
- 復元後に足した op は**続きの番号**を取り、古い cursor が壊れない
- 名簿・個別共有鍵も戻る
- 壊れた payload の行は飛ばすが、ほかの行は読める（`skipped` に数える）
- **復元元は書き換えない**（隔離）
- 世帯を消した後のバックアップには、消したデータが残らない
