# 監視・レート制限・容量と費用（#66）

同期サーバー（Cloudflare Workers + D1）の運用の決めごと。数値のうち「例」と付いたものは想定であり、実測の置き場は Cloudflare のダッシュボード。

## 監視で見るもの

- Cloudflare ダッシュボード
  - **Workers**: Requests、Errors（4xx/5xx）、CPU time（p50/p99）、Duration
  - **D1**: Rows read / Rows written、Storage、Queries
  - **Workers Logs**: `wrangler.toml` の `[observability] enabled = true` で有効。`console.*` の出力をダッシュボードで確認できる
- 死活監視: `GET /healthz` → `200 {"ok":true}`。**認証不要・DB非依存**。外部の稼働監視から定期確認する（[server/README.md](../server/README.md)）。
- 警告の目安（例）
  - 5xx率 > 1% が5分続く → 調査
  - Worker CPU time p99 > 20ms（無料枠は CPU 10ms/リクエスト）→ 有料プラン検討か処理の見直し
  - D1 rows read/日 が想定の2倍 → 調査

## 秘密をログに出さない

- 応答は理由コード（`unauthorized` / `bad_*` / `internal`）だけ。トークン・家庭の本文・世帯idは返さない。
- `console.error` はスタックのみ。クエリ文字列（世帯id・トークン）を含む URL はログに残さない方針とする（監視ログを足す場合も `pathname` のみ）。
- Workers Logs には console 出力だけが乗る。リクエスト本文は保存しない。

## レート制限と濫用対策

### アプリ側（実装済み・変更しない）

- 1回の `POST /ops` は **200 op まで**（超えたら400。端末が分けて送る）
- 本文は **1MB まで**
- `GET /ops` のページは **既定1000件**（`limit=0` で無制限。cursor で繰り返す）
- 世帯idは **16〜64文字の乱数**（推測困難）。トークンは **32文字以上**、サーバーはハッシュのみ保持

### サーバー側（Cloudflare のダッシュボードで設定）

コードには入れず、Cloudflare の Rate limiting rules で持つ（エッジで止めるのが安く確実なため）。

- 例: `/ops` と `/household/*` を対象に、**IPあたり 120リクエスト/分**、超過は **429** でブロック1分
- 例: `POST /ops` は **IPあたり 30リクエスト/分**
- **世帯の乱造**は、最初のアクセスで世帯が作られる仕様のため、上の IP レート制限で抑える
- **1件リンク**の発行は世帯認証が要る（世帯トークンを知る端末だけ）。鍵は **最大7日**で失効。発行もレート制限の対象に含める

### 再試行方針（端末側）

- `429` / `5xx` / タイムアウト: 送信待ちを保持し、指数バックオフで再送（端末は「送信済み位置」で未送信を再送する）
- `400` / `401`: **再送しない**（本文の形、またはトークンの問題）

## 容量と費用の見積り（例）

想定: 世帯 10、端末 3/世帯、1端末 20 op/日。

- op 1件 ≈ 300B（payload 込み）→ 1世帯 60 op/日 ≈ 18KB/日 → 10世帯 ≈ 180KB/日 ≈ **65MB/年**
- Workers リクエスト: 前面同期で 1端末 数十/日 → 全体で**数千/日**（無料枠 100,000/日 に収まる）
- D1 無料枠: rows read 5M/日、rows written 100k/日、storage 5GB。上記規模なら余裕
- 有料: Workers Paid **$5/月**（1,000万リクエスト込み）、D1 は読み書き従量。想定規模では無料〜$5

### 予算と警告条件

- 月 **$10** を超えそうなら通知（Cloudflare の Billing アラート）
- D1 storage **1GB** 超、または Workers リクエスト **50,000/日** 超で調査
- 費用が伸びる要因は **op が追記のみで増え続ける**こと。整理・圧縮はこのIssueの境界の外（別設計）

## 障害・容量超過時の初動

- 担当・通知先: **（所有者が記入。未確定）**
- 手順
  1. `GET /healthz` と Cloudflare ダッシュボードで切り分け（Worker停止／D1障害／レート制限）
  2. レート制限が原因なら規則を一時緩和（自分たちのIPを許可）
  3. D1障害なら復旧手順（#65）に従う。**データを壊す操作・巻き戻しを即実行しない**
  4. 端末は未送信を保持しているので、復旧後に再送される（ユーザー操作は不要）
- ロールバック: Worker を直前バージョンへ戻す（`npx wrangler rollback`）。スキーマは追記のみで、戻さない
