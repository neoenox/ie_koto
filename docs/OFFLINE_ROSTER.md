# オフライン再起動時の名簿復元（#48）

## 原因と変更

保存済みの名前を初期メンバー `me` / `partner` に上書きしていたため、共有名簿の canonical ID と追加メンバーが起動時に消えていた。また旧ID対応表はメモリにしかなく、古い操作の担当を解決できなかった。

- 既存の `member_names` を名簿として読み、全メンバーを復元する。別の重複した名簿形式は増やさない。
- `member_aliases` に旧ID→共有IDを保存する。名簿・本人設定・未送信名と同様に世帯スコープに閉じ込め、旧データの初回移行にも含める。
- 未送信の改名と追加を、起動時にもサーバー名簿の適用時にも優先する。同期中に増えたローカルメンバーを古い応答で消さない。
- 2台が同じメンバーを別名に改名した場合は後勝ちとし、負けた側への通知はしない。同時編集は稀という設計判断（#75）。
- 古い操作ログは書き換えず、射影時に旧IDを読み替える。名前だけの旧保存形式も引き続き読む。不正な対応表は既存の安全な文字列マップ読取で無視する。

実装: [IssueStore](../lib/store.dart)、[DeviceStorage](../lib/sync/storage.dart)。

## 自動テスト

[回帰テスト](../test/member_restoration_test.dart) は修正前に4件すべて失敗することを確認した。修正後は以下を検証する。

1. オフライン再起動で3人の共有名簿、第三メンバーの本人設定、旧担当、操作ログを復元。
2. 未送信の追加・改名・その担当を維持し、古いサーバー名簿でも消さない。
3. 名前だけの旧保存形式から追加メンバーも復元。
4. 世帯切替で名簿・本人・旧ID対応・未送信名が混ざらない。
5. 非同期保存の `flush()` 完了後、新しい保存インスタンスから復元。
6. 壊れた旧ID対応表があっても旧形式の名前・用事を読める。

## 実Chrome検証（2026-10-08）

本番ではなく、ローカルWorker HTTPハーネスとファイルSQLite DBを使った。新しいWebビルドを別の静的オリジンで配信し、独立した2つのChromeセッションで検証した。

1. disposable世帯に「あき／はる／そら」を登録。Aの本人を「そら」に変更。
2. Aの画面から「名簿復元を確かめる用事」を「はる」担当で追加。Bに自動受信し、両方が同期済みになった。
3. テストAPIプロセスだけを停止し、A・Bともページを再読み込み。両画面に用事と担当「はる」が残った。Aの設定でも3人と本人「そら」が維持された。
4. API停止中にAの画面から「はる」を「春」へ改名し、「なつ」を追加。Aを再読み込みして、担当「春」、4人の名簿、本人「そら」が残ることを確認。
5. 同じSQLite DBでAPIを再起動。ブラウザの手動再試行や再読み込みをせず、定期同期でBの担当表示が「春」になり、設定に「なつ」が追加された。Bの本人は「あき」のまま。

これはAPI停止中のWeb再起動と復旧を検証したもので、Android実機のプロセス強制終了・OSによる背景復帰、本番D1、読み込み前のキャッシュなし完全オフライン起動まで保証するものではない。ローカル保存完了前の強制終了についても今回の保証範囲には含めない。
