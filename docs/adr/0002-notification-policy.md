# ADR 0002: 通知の方針（アプリ内は済み、OS通知は当面見送り）

状態: 採用

## 背景

通知は設計上3種だけと決めている（朝の要約・期限当日・自分の担当になった瞬間。[VALIDATION.md](../VALIDATION.md) の「通知は最小」、[DECISIONS.md](../DECISIONS.md) の禁止リスト）。実装はアプリ内まで済んでいる。ホームのお知らせ1行が期限当日・すぎたもの・今日の自分を兼ね、起動時同期の担当通知が出る（[lib/notices.dart](../../lib/notices.dart)）。

OS通知は未実装のまま「[SYNC_DESIGN.md](../SYNC_DESIGN.md) §10」に残っている。前面同期は10秒ごとだがバックグラウンドでは止まる（[FOREGROUND_SYNC.md](../FOREGROUND_SYNC.md)）。前提は静かさ・依存最小・アカウント無し・第三者SDK無し（[PRIVACY.md](../PRIVACY.md)）。

この文書は #52 の設計Issueとして、何を通知し何を通知しないか、重複・自分の操作・定期案件・夜間をどう抑えるか、権限拒否・単独利用・バックグラウンド・オフライン・ロック画面での露出をどう扱うかを固定し、OS通知を実装するか見送るかを決める。

## 決定

### 通知する3種（増やさない）

1. **自分の担当になった瞬間**（イベント）: 担当者が「自分」へ変わり、直前は自分以外で、その変更の操作者が自分でないとき、遷移ごとに1回だけ。操作ログの担当変更opで判定する。
2. **期限当日**: その日が期限でまだ終わっていないもの。1日1回・まとめて1件。文言は件数のみで案件タイトルは含めない。0件なら出さない。
3. **朝の要約**: ホームのお知らせ1行が兼ねる（実装済み）。期限当日・すぎたもの・今日の自分の件数を1行にまとめる。出す内容が無ければ行自体を出さない。

### 通知しないもの

- **コメントの到着**は通知しない（3種に含めない）。静かさが差別化であり（[VALIDATION.md](../VALIDATION.md)）、コメントは詳細を開いたときの文脈で足りる。
- **新しい依頼の追加**は、「自分の担当になった瞬間」に当たるときだけ通知する（他人が自分のために追加して自分が担当になった場合）。自分で追加したものは通知しない。
- **新機能の案内・再通知・催促・未読件数**は作らない（非対象。バッジや未読件数の競争化をしない）。

### 抑制の条件

- **自分の操作**: 操作者 ==「この端末を使う人」の変更では通知しない（自分の操作に通知しない）。
- **重複**: 担当になった瞬間は遷移ごとに1回だけ。同じopの再適用・再同期で再度出さない。期限当日は（種類, 日付）で1回に集約し、同じ日に何度開いても再通知しない。
- **定期案件**: 「次を出す」で生まれる定期の担当は「自分の担当になった瞬間」に数えない（生成のたびに鳴らさない）。期限当日の集約にだけ載せる。
- **夜間**: OS通知の静穏時間は端末ローカル時刻で21:00〜07:00。この間は送らず、07:00以降にまとめて1件にする。期限当日の集約は07:00以降の最初の起動・前面化で出す。アプリ内のお知らせ行は静穏時間でも出す（利用者自身が開いた画面を妨げない）。

### 状態ごとの挙動

- **単独利用**（同期未設定）: サーバーも相手もいないため通知対象が無い。OS通知は求めず、ホームのお知らせ行だけを使う。
- **権限拒否**: アプリは通常どおり動く。OS通知は一度だけオプトインを出し、拒否されたら再要求・催促しない。代替はアプリ内のお知らせ行。
- **バックグラウンド**: 前面同期は背景で止まる。したがって「起動時同期」を根拠にした通知は、アプリを閉じている間は届かない。閉じている間に気づかせるにはサーバー起点のプッシュが要る（配信基盤の項で評価）。
- **オフライン**: 新しい通知は作らない。担当変更の通知は受け取ったopから計算するため、同期が次に成功した時点で遅れて届く。同時編集の相手には通知しない（[OFFLINE_ROSTER.md](../OFFLINE_ROSTER.md) の方針に合わせる）。

### ロック画面での露出

- OS通知の本文に家庭情報を出さない。案件タイトルやメンバー名を含めず、「いえこと: 家のことを1件」のように件数のみ。開いて初めて中身が見える。
- 内容を出すかどうかは将来の端末設定トグル（既定OFF）。鍵・秘密の扱いは [SECURITY.md](../SECURITY.md) に従う。

### 配信基盤と費用（見送りの判断）

- 同期は Cloudflare Workers + D1（既設）。第三者SDK無しでも、Android は定期取得（WorkManager）＋ローカル通知、Web は Web Push(VAPID)＋service worker で実装しうる。
- **FCM は採用しない**: 第三者SDK・Google依存で、静かさ・依存最小・プライバシーの方針に反する。
- Web Push は購読エンドポイントのサーバー保管、VAPID鍵の管理、service worker を足す。費用は家族規模でほぼ無視できる（[OPERATIONS.md](../OPERATIONS.md) の$10アラート内の見込み）が、複雑さの増分が大きい。
- Android の定期取得は最短15分間隔でDozeの影響を受ける。「当日中に気づく」の助けにはなるが時刻は保証しない。Android 13+ は通知権限が実行時。
- いま実装して得る便益（閉じている間の即時性）より、増える複雑さ・保証できない配達・静かさの後退が上回る。

### UI予算・対象・検証

- OS通知は画面外なので、アプリのUI予算（ナビ3つ以下・ホームの情報量を増やさない・バッジ無し）を変えない。
- 対象: Android（主）と同一ドメインのWeb（後に）。iOS は対象外。
- 検証（いま確定できる範囲）: アプリ内は [lib/notices.dart](../../lib/notices.dart) の文言をテストで担保する。OS通知は見送りのため実装検証は持たない。

## 結果

- 通知はいまのアプリ内のみで、コード変更は無い。OS通知の実装Issueは、下の見直す条件が満たされるまで作らない。
- 静かさを維持し、第三者SDKとアカウントを増やさない。
- 「起動時同期」を根拠にする通知は、閉じている間は届かないことを明記した（実装時の約束違反を防ぐ）。

## 見直す条件

- 実際に使い続け、期限の取り逃しが測れる（例: 期限当日に未完了のまま翌日を迎えた回数）。
- 世帯が複数で運用され、閉じている間に気づけないことが実際の問題になったとき。
- 手順4（Webビルドを同一ドメインに置く）以降で、Web Push を足す土台（service worker）が揃ったとき。

実装する場合の最小形: Android = 定期取得＋ローカル通知、Web = Web Push(VAPID)。本文は件数のみ、静穏時間は21:00〜07:00、対象は「自分の担当になった瞬間」と「期限当日」の2種（朝の要約は行のまま）。
