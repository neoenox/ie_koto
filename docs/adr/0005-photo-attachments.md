# ADR 0005: 写真・添付（型番や故障状態）は当面見送り。採るなら別経路

状態: 見送り（この版では実装しない。#58 の設計評価として記録。実装Issueは分割しない）

## 背景

- 電球の型番・水道の故障状態は、文章より写真が向く（[#58](https://github.com/neoenox/ie_koto/issues/58)）。
- 現状、写真を扱う op は無い。`EventKind.photo` と詳細の「写真が追加されました」表示だけが残っていて、どの op からも生成されない**到達しない分岐**（[lib/model.dart](../../lib/model.dart) の `EventKind.photo`、[lib/detail_page.dart](../../lib/detail_page.dart) の `_Timeline`）。枠は実質デッドコードで、機能があるように見せてはいないことを今回あらためて確認した。
- 同期は op を預ける形で、**サーバーは op の中身を解釈しない**（[SYNC_DESIGN.md](../SYNC_DESIGN.md) §8.5）。本文は 1MB 上限（`MAX_BODY_BYTES`）、保存は D1（SQLite）。画像はこの経路に載らない。
- 単独利用が既定で、同期は任意。1件リンクは案件に限定した共有鍵（scope・サーバー側期限。[#2](https://github.com/neoenox/ie_koto/issues/2) で導入済み）。
- 権限は `INTERNET` のみ。個人情報を扱わない方針（[PRIVACY.md](../PRIVACY.md)）。

## 決定

**この版では写真・添付を採用しない。** 理由は「いまの価値 < 費用と新しいリスク」（下の比較）。ただし #58 の受け入れ条件（保存先・費用・圧縮・再試行・オフライン／認可・メタデータ・削除・引っ越し／外部URLの扱い／取り込みと検証）は、**採るならこうする**として決めておく。見直す条件が満たされたら、この節を前提に実装Issueへ分割する。

### 1. 採るなら: 保存先と費用

- 画像は D1 に置かない。**Cloudflare R2**（オブジェクトストレージ）に置き、op は**参照だけ**を持つ `photo` op にする（`data.key`・`data.w`・`data.h`・`data.bytes`・`data.sha256`）。op 本体は今と同じく軽いまま。
- 配信は Worker 経由の限定エンドポイント。R2 の公開URLや署名付きURLは使わない（誰でも読めるURLを作らない）。
- 容量・費用の上限を先に決める: 1件あたりの上限（例 3MB・長辺2048px）、世帯あたりの合計（例 500枚／500MB）。超過はサーバーで数えて断る。無料枠と単価の見積もりは [OPERATIONS.md](../OPERATIONS.md) に追記する。
- 端末側で**圧縮してから**送る（長辺2048px・JPEG品質80目安）。原寸は残さない（費用とバックアップの両方が膨らむため）。

### 2. 採るなら: アップロード・失敗・オフライン

- 送信は op と別経路（`POST /photo` → R2）。`photo` op は**アップロード成功後**に追記する（参照だけ残って実体が無い状態を作らない）。
- 失敗時は再試行。送信待ち（outbox）と同じ考え方で、未送信の写真を端末に残し、次の同期で送る。オフラインで撮っても、実体と op の順序が崩れないようにする。
- 削除は R2 のオブジェクトも消す（追記のみの原則は op に限る。ゴミ箱は作らない）。

### 3. 採るなら: 認可（世帯・1件リンク）

- 世帯: 既存と同じ世帯トークンで認可。世帯の全員が読める。
- 1件リンク: **その案件に紐づく写真だけ**を、共有鍵（scope・サーバー期限）で読めるようにする。世帯の他案件の写真は渡さない。リンクの期限が切れたら写真も読めない。
- **任意の外部URLを表示するだけの案は、添付の代替にしない**（下の代替案）。

### 4. 採るなら: メタデータ・プライバシー

- **EXIF（特にGPS）を端末で必ず剥がしてから**送る。位置情報を扱わない方針（[PRIVACY.md](../PRIVACY.md)）を崩さない。
- [PRIVACY.md](../PRIVACY.md) に写真の行を足し、Google Play のデータ申告（写真と動画）を更新する。ロック画面・通知本文には出さない（[0002](0002-notification-policy.md)）。
- 端末内は平文（現行方針）。写真も暗号化しない点を明記する。

### 5. 採るなら: 削除・失効・バックアップ・引っ越し

- 案件の削除: op は残し、参照が消えた写真の実体は遅延削除の対象にする。
- 世帯の削除・rotate: 当該世帯のオブジェクトを削除対象にする。
- バックアップ: D1 のポイントインタイム復元・手動ダンプは **op のみ**。R2 の写真は別に保全しない（戻らない前提を [RECOVERY.md](../RECOVERY.md) に明記する）。
- 引っ越し（書き出し・読み込み）: JSON に画像は埋め込まない。**写真は同期先ごとに取り直す**（世帯に残っていれば見え、無ければ見えない）。

### 6. 採るなら: 取り込みと検証

- Android: カメラ／ファイル選択。権限を増やす（`CAMERA` または `READ_MEDIA_IMAGES`）。Play の申告を見直す。
- Web: `<input type="file" accept="image/*" capture>`。端末に保存はしない（1件リンクと同じ）。
- 検証: 実体と op の順序／オフライン撮影→復帰送信／圧縮後のサイズ／EXIF除去／1件リンクで他案件の写真が取れない／期限切れ／容量上限／世帯削除で消える／引っ越し後に見える・見えない。

### 7. デッドコードの扱い（今回の小さな確認）

- `EventKind.photo` は wire の前方互換のため enum に残すが、**どの op からも生成されず到達しない**ままにする。写真を約束する導線（追加ボタン・「写真を追加」）は作らない。
- 詳細の「写真が追加されました」は `photo` op を採らないかぎり現れない。**見直す条件が満たされるまでは触らない**（今のままで害はない）。

## 代替案との比較

- **採用（R2 ＋ 圧縮 ＋ 権限追加 ＋ メタデータ剥がし）**: 型番・故障状態の共有は本質的に良くなる。しかし (a) 第二の保存系（R2）と新しい認可経路、(b) 新しい権限と Play 申告の変更、(c) EXIF・世帯可視・バックアップ対象という新しい個人情報、(d) 圧縮・再試行・オフラインの実装量、が一気に増える。**当面の用途は、既に入れたメモ（型番は文字で足りる）とコメント（故障の経緯）でほぼ代替できる。** P3・初回リリース前という位置づけとも合わない。
- **任意の外部URLを表示するだけ**: 保存も圧縮も不要に見えるが、**消えたリンク・権利不明の画像・位置情報入りの画像**を世帯の画面に持ち込み、世帯トークンでは守れない。「世帯に見える」という共有の説明も崩れる。**添付と同等に扱わない**（#58 の受け入れ条件）。リンクはコメント本文のテキストで足りる。
- **メモで代替（採用済み）**: 型番・連絡先・注意点は `note`（[0004](0004-issue-memo.md)）に文字で残せる。故障の推移はコメントに残る。

→ **見送り。** メモ（[#57](https://github.com/neoenox/ie_koto/issues/57)）で当面の用途は満たす。

## 結果

- リリースは「テキスト＋メモ＋コメント」で完成させ、第二の保存系・新しい権限・新しい個人情報を持ち込まない。
- 判断と根拠、見直す条件をここに残す。採用時はこのADRを更新し、実装Issueへ分割する。
- 「写真があるように見える」UIは作らない（`EventKind.photo` は到達しないまま）。

## 見直す条件

- 内部テスト（[RELEASE_ACCEPTANCE.md](../RELEASE_ACCEPTANCE.md)）の継続利用で、**型番や故障状態がメモ・コメントの文字では足りない**という具体的な声が出たとき。
- R2 と新しい権限（＋ Play 申告の変更）と EXIF 除去を受け入れる用意ができ、初回リリースが安定したあと。
- セキュリティレビュー（[SECURITY.md](../SECURITY.md)）で、写真の認可（世帯・1件リンク）が既存の共有鍵と同じ強さで説明できると確認できたとき。
