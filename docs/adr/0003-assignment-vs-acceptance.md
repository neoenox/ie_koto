# ADR 0003: 「割り当て」と「引き受け」の区別（新しい受諾状態は作らない）

状態: 採用

## 背景

家族が担当を割り当てても、相手が認識・了承したとは限らない。1件リンクには「やる」があるが、通常の共有画面は担当と受諾を区別しない（#53）。一方で、UI予算と言葉リスト（[DECISIONS.md](../DECISIONS.md)）は状態を増やすこと・承認フローを禁じている（非対象: 業務用の承認フロー、依頼者による全件の完了承認）。

担当は `OpKind.assignee`（`data.assigneeId`）として操作ログに追記され、射影は全順序で最後の1つが勝つ（[lib/sync/log.dart](../../lib/sync/log.dart) の `compareOps`: 論理時計 → 端末id → op id）。opには書いた人（`memberId` = 操作者）が残る。1件リンクの「やる」も同じ `assignee` op で、操作者と担当者が同じになる（[lib/one_page.dart](../../lib/one_page.dart)、[server/src/index.js](../../server/src/index.js) の share 検証）。

「対応待ち」（`IssueStatus.waiting`）は「家族・業者の対応を待つ」状態で、割り当ての了承とは別物（[lib/detail_page.dart](../../lib/detail_page.dart)）。この ADR はその流用も禁じる。

## 決定

### 1. 意味の定義（opログから導出し、フィールドは増やさない）

- **割り当て** = 担当を変えた操作者と新しい担当者が別人（操作者 ≠ 担当者）。「お願い」であり、了承ではない。
- **引き受け** = 操作者と新しい担当者が同一（操作者 = 担当者）。「自分で引き受けた」。
- **だれでも** = 担当者を null にする（割り当ての返却）。
- **既読は追跡しない**。担当を割り当てても「読んだ」「了承した」とは表示しない。

### 2. 受諾（承認）という状態は作らない

状態語は「やること／おわった（詳細のみ 対応待ち）」のままとし、「依頼中」「承諾待ち」のような語を増やさない。**対応待ちを受諾の意味に流用しない**（対応待ちは「待っている相手がいる」の意味）。

### 3. 最小操作（全家事に受諾を強制しない）

- アプリ内: 詳細の担当で「自分」を選ぶ＝引き受け。家族を選ぶ＝割り当て。
- 1件リンク: 「やる」＝担当を自分にする＝引き受け。通常画面の「担当＝自分」と同一の op（`kind=assignee`, 操作者=担当者）。意味を揃える（実装済み。変更なし）。
- 明示の引き受け操作は上の2つだけ。既定は「割り当てられたら担当として見える」で、受諾は求めない。

### 4. 段取り

- **担当変更**: `assignee` op を追記。射影は最後の1つが勝つ（全順序で収束）。
- **取り消し／断り**: 専用の「断る」は作らない。断りは担当を変える（だれでもに戻す、または自分以外にする）ことで表す。アプリのその場の取り消しは完了・再開が対象。
- **別人による完了**: 誰でも1タップで完了できる（承認ではない）。完了の操作者は履歴に残り、担当者である必要はない。
- **オフライン同時操作**: 両端末のopが突き合わさり、`compareOps` の全順序で一意に収束する。相手の担当変更は通知しない（[0002-notification-policy.md](0002-notification-policy.md)）。
- **既存案件の移行**: 新しいフィールド・状態を足さないため移行は不要。旧ID（`me`/`partner`）は名簿の `aliases` で読み替える。操作者（`memberId`）が無い古いopのactorは推測しない（[lib/store.dart](../../lib/store.dart) の `_event`）。

### 5. UI評価（採用・見送りの結論）

- A: Aが追加してパートナーに割り当て → Bの端末に行とパートナーのチップ。Bが完了。受諾は不要（成立）。
- B: Aが1件リンクを送り、アプリ未導入のCが「やる」→ 担当を引き受け、Aの履歴に残る（成立）。
- C: だれでもを、Bが「担当＝自分」で引き受ける（成立）。
- D: Aが割り当てたがBができない → Bが担当を変える（自分以外／だれでも）。断る操作は作らない。
- E: AとBが同時に担当を変更 → opの全順序で収束。相手に通知しない。
- 意図の見え方: 詳細のタイムラインに「パートナーが担当になった」＋操作者（誰が）が出るため、割り当て（家族がした）と引き受け（本人がした）は読み分けられる。
- **結論: 追加の状態・承認・既読・専用UIは見送る。** 担当＝自分／家族の選択と「やる」で足りる。

### 6. 実装への分割

見送りのため実装Issueは作らない。将来、利用者の混乱が観測された場合の最小案は「詳細のタイムラインで、操作者と担当が同一のときだけ『自分で引き受けた』と出す」等で、状態・op・フィールドは増やさない。

## 結果

- コード変更なし。担当が割り当てか引き受けかは op ログ（操作者と担当者の一致）で決まり、サーバーは op を解釈しない現行方針を保つ（[SYNC_DESIGN.md](../SYNC_DESIGN.md)）。
- 「割り当て＝了承」と誤解させる表示・既読・承認フローを追加しない方針を固定した。
- 「対応待ち」が受諾と別物であることを明記し、流用を防ぐ。

## 見直す条件

- 「頼んだのに相手が了承したか分からない」という困り方を実際に観測したとき。
- 世帯が増え、役割や権限（子ども・ゲスト）を分ける必要が出たとき（別の認可設計として扱う）。
