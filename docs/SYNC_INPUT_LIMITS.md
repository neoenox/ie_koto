# 同期入力の数値境界（#67）

## 確認した問題

ローカルのWorkerとメモリSQLiteに `lamport=9007199254740992`（2^53）のadd opをPOSTすると、修正前はHTTP 200、accepted=1になった。JavaScriptではこの値に1を足しても同じ値になる。

クライアントのDeviceは受信した最大lamportを自分の時計へ採用し、次の書き込みで1増やして操作IDを生成する。そのためWebの整数精度を超える入力は、以後の操作IDの一意性を壊す危険がある。実Webアプリの操作までの再現は今回未実施。

## 最小修正

サーバーのparseOpはlamportを1〜2,147,483,647の整数に限定する。範囲外は400で拒否し、opsへ保存しない。32bit上限はWebの精度限界より十分低いプロトコル上限として採用した。既存データの移行・削除はしない。今回のparseOpはPOST受付にだけ使われ、GETのpullOpsには適用されないことを確認した。したがって保存済みの範囲外opを今回の変更だけでは排除できず、既存データの状況確認とクライアント防御は必要。

境界回帰テストは0、負数、小数、上限+1、2^53の拒否と、1・上限の受理を検証する。修正前は上限+1を受理して失敗、修正後はサーバー全21テスト成功。さらにFlutter→実HTTP→Workerの同期・1件リンクE2E全5テストが成功し、通常同期・ページング・重複排除・限定リンク経由の担当共有の回帰がないことを確認。
