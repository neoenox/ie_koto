# 前面同期と保存・送信の表示（#50 / #51）

## 方針

WebSocket購読は追加せず、前面で10秒ごとに差分同期する。起動・復帰時はすぐ同期し、通常の編集は2秒でまとめる。バックグラウンド・終了・世帯切り替え時はタイマーを止める。すでに通信中の回は完了を待つが、終了したセッションの応答はストア・cursor・担当通知に反映しない。

同期は同じin-flight Futureに合流させ、定期取得・自動送信・手動再試行が重ならないようにする。通信中に追加された変更はその回の後半または次の定期同期で送る。通信失敗でも未送信opは残し、次の定期同期で再試行する。10秒は開始間隔であり、通信時間・ブラウザのタイマー制限・API障害まで含めた配達保証ではない。メンバーの追加・改名も同じ自動送信に合流し、同期飛行中は次の定期同期（最大10秒後）を待つ（#73）。

## 表示の意味

- **端末に保存中**: 保存先の非同期書き込みの完了待ち。
- **端末に保存済み・送信待ち**: 保存先の成功応答は受け取ったが、サーバーには未確認の変更がある。
- **送信・同期中 / 同期中**: サーバーとの処理中。
- **同期できません**: 直近の同期に失敗。自動再試行を続ける。手動の「再試行」もある。
- **端末に保存できません・閉じずに再試行**: ローカル保存失敗。未保存内容をメモリに保持し、保存を再試行する。閉じると失われる可能性がある。
- **サーバーと同期済み**: 直近の同期が成功し、端末の未送信変更がない。相手の画面表示、既読、受諾を意味しない。

単独利用では同期状態を表示しない。接続設定があるというだけでオンライン扱いしないため、ホームの設定入口は「家族と共有」と呼ぶ。

SharedPreferencesのFutureとboolを確認し、失敗したキーの最新値を保持する。保存成功はOS/ブラウザからの成功応答までであり、ストレージ障害・利用者によるデータ削除・OSによる強制終了に対する永久保証ではない。受信記録の保存失敗時はcursorを進めず、再取得できるようにする。

## 実Chromeでの確認記録

2026-10-08: ビルド済みアプリとメモリDBのテストWorkerを使い、agent-browserの独立した2セッションで確認した。本番APIには接続していない。

- Aの画面から追加 → Bの一覧へ自動受信。
- Bの画面から完了 → Aの未完了一覧から自動で消える。
- AだけAPI宛てfetchを失敗させて追加 → 「同期できません・送信待ち」、Bには未到着。
- fetchを戻す → 手動同期・リロードなしで両方の一覧に届き、「サーバーと同期済み」へ戻る。

この確認ではブラウザ全体の通信を切っていない。コメント・担当変更・取り消し、OS背景復帰、ブラウザプロセス再起動は今回の独立2ブラウザ操作では未検証。ライフサイクル相当の停止・復帰と終了後の応答破棄はユニットテストで確認している。

### ブラウザ検証の注意

Flutter Webは古いservice worker/HTTPキャッシュで以前のバンドルを起動する場合がある。ビルド成功だけで新しい画面を確認済みとしない。今回も古いヘッダーが出たため、新しいローカルポートで配信し、「家族と共有」「サーバーと同期済み」が実際に描画されることを確認してから操作した。SharedPreferencesの文字列はlocalStorageではJSON文字列として格納されるため、テスト設定を直接入れる場合は二重JSON化が必要。通常利用では設定画面を使う。
